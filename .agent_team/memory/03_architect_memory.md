# 03_系统架构师 长期提炼记忆库 (ADRs & 架构决策)

## 1. 架构决策记录 (ADRs)
* **ADR-001: 边缘 Serverless 与 Docker 双模架构**:
  - **背景**: 用户群体同时包含 Cloudflare Pages 免费边缘托管用户与私有 VPS / NAS Docker 部署用户。
  - **决策**: 核心 API 保持在 `functions/`，Docker 部署使用 `deploy/server/` 轻量适配器模拟 Pages Functions 运行时，保证单套核心逻辑双模复用。
* **ADR-002: D1 与 SQLite 数据统一**:
  - **背景**: Cloudflare D1 底层基于 SQLite。
  - **决策**: 本地开发与生产环境统一采用标准 SQLite / D1 SQL 方言，避免使用专有特定数据库语法。
* **ADR-003: 时空足迹两阶段加载协议与高德底图坐标闭环 (REQ-001)**:
  - **背景**: 随照片积累，地图全量散点数据传输过大易引发卡顿；CartoDB/OSM 国际底图存在 API Key 水印且国内中文地名支持弱；国内高德底图使用 GCJ-02 火星坐标系。
  - **决策**: 
    1. 采用两阶段加载：阶段 1 仅返回散点打点所需的轻量遥测数据（`{id, lat, lng, name, dir, date}`，60KB/2000张）；阶段 2 仅在展开抽屉时按需拉取长篇游记故事与照片详情。
    2. 底图选型方案 1：采用高德浅色极简底图（`style=7`），无水印、全中文、加载快速。
    3. 全链路坐标纯度与双向映射机制：D1 数据库、存储、上传 EXIF、逆地理编码坚持 **100% WGS-84 坐标纯度**；前端渲染时通过轻量算法动态转换为 GCJ-02 呈现在高德瓦片上，用户在地图选点打卡时将点击的 GCJ-02 坐标逆变换为 WGS-84 后持久化，完美解决偏移与水土不服。
* **ADR-004: 双写策略与 Telegram 缩略图防限流机制 (REQ-001)**:
  - **背景**: 纯 Telegram 存储存在原图并发读取触发 429 限流风险；同时项目支持 D1 与 KV 两种引擎。
  - **决策**:
    1. 抽屉多图画廊强制使用 `/file/{id}?width=400&fit=cover` 边缘裁剪为轻量 WebP，仅在全屏看图时拉取原图。
    2. 地理数据同时写入 D1 物理列（带空间索引）与 `metadata` JSON 字符串，实现跨引擎高可移植性。

## 2. 演进防坑指南
* 新增接口必须保持向后兼容，防止影响已发布的移动端快捷指令或第三方客户端。
* 数据库迁移必须提供 UP 和 DOWN 回滚脚本。
* 严禁在并发研发期启动后台监听端口，遵循零端口占用与单例托管原则。
* 无论使用何种瓦片底图，物理数据库严禁存储二次偏转坐标（如 GCJ-02/BD-09），永远以 WGS-84 作为通用真理基准。
